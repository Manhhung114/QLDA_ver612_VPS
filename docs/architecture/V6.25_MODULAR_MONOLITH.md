# V6.25 — Modular Monolith

V6.25 starts the architectural migration from a flat repository of versioned modules to a modular monolith under `src/qlda/`.

## Goals

- Preserve all V6.24.5 business behavior and PostgreSQL data.
- Introduce stable module namespaces before moving large implementations.
- Keep one deployable application and one PostgreSQL database.
- Prevent a risky big-bang rewrite of BOQ, IPC, VO, Schedule and AI code.
- Prepare V6.26 Service Layer and V6.27 FastAPI without duplicating business logic.

## Initial package layout

```text
src/qlda/
├── infrastructure/
├── presentation/
├── shared/
├── module_registry.py
├── runtime.py
└── modules/
    ├── boq/
    ├── ipc/
    ├── vo/
    ├── schedule/
    └── excel/
        ├── jobs.py
        └── worker.py
```

## Migration rule

V6.25 uses a strangler migration. New callers import the stable `qlda.*` namespace. Existing V6.22-V6.24 root modules remain compatibility implementations until each domain is moved behind its package boundary. This keeps schema, calculations, permissions and file workflows unchanged during restructuring.

The first production cut-over is the Excel worker:

```bash
python -m qlda.modules.excel.worker --poll-seconds 2
```

The modular entrypoint delegates to the proven V6.24.5 implementation today. Later V6.25 commits can move BOQ/IPC/VO/Schedule internals without changing the systemd command again.

## Dependency direction

- `presentation` may call public module APIs.
- business modules may use `infrastructure` and `shared`.
- modules must not import Streamlit directly in their core/package facades.
- cross-domain calls should target another module's public API rather than private implementation files.
- root versioned modules are temporary compatibility adapters, not new extension points.

## Non-goals in V6.25

- No database schema rewrite.
- No business formula change.
- No permission/workflow change.
- No microservices split.
- No FastAPI replacement of Streamlit yet.

## Next step

V6.26 introduces a Service Layer and progressively replaces monkey-patch/direct-database calls with explicit application services while keeping these V6.25 module boundaries.
